# Latitude 7390 / BCM5880 `0a5c:5833` bring-up evidence

This is a privacy-safe summary derived from local hardware observations. Raw
USB payloads, device-node identifiers, process identifiers, timestamps, and
complete runtime logs are intentionally excluded.

## Test environment

- Distribution family: Arch Linux
- Laptop: Dell Latitude 7390
- Device family: Broadcom BCM5880 / ControlVault2
- USB ID: `0a5c:5833`

Interface 0 exposed the transport endpoints also seen on `0a5c:5834`:

```text
0x01  bulk OUT
0x81  bulk IN
0x85  interrupt IN
```

Endpoint equality was treated as an initial compatibility indicator, not as
proof of full protocol equivalence.

## Staged transport result

The transfer-free enumeration and claim/release-only stages completed. One
explicitly allow-listed `cv_get_ush_ver` (`0x39`) request then produced:

- a complete 44-byte write;
- an interrupt completion reply;
- a 44-byte bulk response carrying command ID `0x39`;
- no timeout or crash.

The raw request and response payloads are not published.

## Enrollment research result

Later repository-local experiments established:

- `0x89 → 0x8a → new capture` recovery works on the tested device.
- A bounded second UpdateEnrollment after `0x59` returns native `0x89`.
- That transition allows accepted progress to continue beyond the former
  three-sample boundary.
- Completion remains zero and the host stage counter can exceed ten.
- State 2, template commit, and verification have not been reached.

The bounded `0x59` behavior is a diagnostic hypothesis, not a completed
driver fix.

A later Windows A21 reference run successfully enrolled on the same device.
Its privacy-safe structural trace contained four accepted `0x6c` operations,
then two `0x6e` operations with differently sized replies, and no visible
`0x6f` application-message header. See
`windows-a21-enrollment-runtime.md`. This shifts the immediate comparison to
the Windows and Linux initialization/capture inputs that precede `0x6c`.

Two independent failed Windows controls each accepted three `0x6c` replies,
returned a shorter protected reply for the fourth, and discarded through
`0x6d`. A third control accepted one update before the device reset from
`0a5c:5833` to the single-interface `0a5c:5831` identity. A standard USB reset
did not change that identity; a complete host power-off restored `5833` and
all interfaces without a device problem. These controls are structural
evidence only: protected Windows replies do not prove a numeric mapping to
Linux status `0x59`.

A later one-attempt Linux fresh-boundary control reached accepted progress
`1/10`. Its structural trace was `0x8a`, capture `0x66`, rejected update
`0x6c`, recovery `0x8a`, capture `0x66`, accepted incomplete update `0x6c`,
then a fresh `0x66`. The stock state machine did not send `0x8a` between the
accepted update and the final capture. Four lift-and-touch attempts produced
no further completed capture. Cancellation emitted `0x68`; no commit-family
`0x6e` or `0x6f` was observed. The capture had zero packet drops and the
device remained `0a5c:5833`.

## Privacy statement

No raw fingerprint features, biometric templates, enrollment tokens, capture
payloads, device serial numbers, user identifiers, or authentication

## Conclusion

Probe, open, capture, and bounded retry recovery work on the tested BCM5880
device. Enrollment completion, template commit, and verification remain
incomplete.
